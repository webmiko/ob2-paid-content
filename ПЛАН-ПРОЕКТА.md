# План проекта: OB2 — платформа платного контента

**Дата:** 2026-06-06 (стек v1: SPA + sync Stripe; Celery — опционально v2)  
**Python:** 3.14+ (инструкция v3.0)  
**Статус:** итерация 0 — план и инфраструктура

---

## Описание проекта

Платформа публикации записей: бесплатные материалы доступны всем без регистрации;
платные — только авторизованным пользователям с оплаченной разовой подпиской.
**Монорепозиторий:** JSON API (Django + DRF) и **SPA** в `frontend/` (React + Vite).
Регистрация по телефону, JWT, оплата Stripe Checkout (**sync** success URL в v1).

---

## Цели проекта

1. CRUD публикаций с разделением free/paid и проверкой доступа.
2. Регистрация и вход по номеру телефона + JWT для API.
3. Разовая подписка через Stripe Checkout.
4. Docker Compose (db, web, nginx, SPA), README, покрытие тестами ≥ 85 %.
5. **Production:** без утечек секретов и PII; защита от SQL-инъекций, XSS, CSRF, IDOR.
6. **Деплой на ВМ:** GitHub Actions (test → lint → build → deploy), Nginx + SPA artifact.

## Выбранный стек v1 (баланс: безопасность · простота · поддерживаемость)

Компромисс между «чистым Django» и полным **lms-backend**. Берём лучшее из обоих по трём критериям.

| Компонент | v1 (основной путь) | Не в v1 | Почему |
|-----------|-------------------|---------|--------|
| DRF + JWT | да | — | SPA и API; один механизм auth |
| React SPA | да | — | современный UI; nginx + dist |
| CORS | да | — | dev `:5173`, prod — origin ВМ |
| drf-yasg | только `DEBUG=True` | открытый Swagger в prod | меньше attack surface |
| Stripe Checkout | да | — | разовая подписка по ТЗ |
| Активация подписки | **sync** success URL → `activate_subscription()` | — | проще, меньше moving parts |
| Celery + Redis | **нет** | webhook async, beat | избыточно для one-time pay в v1 |
| CI/CD на ВМ | test → lint → build → deploy | — | как lms; без лишних сервисов |
| Compose | db + web + nginx + frontend build | redis, worker, beat | 4 сервиса вместо 7 |

**Опционально v2** (после зелёных тестов итерации 4): Redis + Celery + Stripe webhook —
та же `activate_subscription()`, без второго алгоритма. См. раздел «Расширение v2».

### Неявный фактор: аутентификация SPA + API (+ admin session)

Клиент SPA и REST API работают на **JWT**; Django admin — **session**. Зафиксировать до итерации 2:

| Канал | Механизм | Где используется |
|-------|----------|------------------|
| SPA (`frontend/`) | access в memory; refresh в `localStorage` | список/деталь постов, CRUD, оплата |
| REST API | `Authorization: Bearer` | те же endpoints, Postman |
| Django admin | session cookie | `/admin/` только |

**Связка:** SPA получает access/refresh через `/api/token/` и register; refresh до истечения access.
Проверка подписки — **одна функция** `users.services.access.user_has_active_subscription(user)`
для permissions и serializers. Логику доступа **не дублировать** во фронте — только UI
(paywall, CTA); источник истины — API.

## Безопасность production (обязательно)

Проект выводится в **production**. Безопасность — сквозное требование всех итераций, не отдельная
«фича» в конце. Ниже — правила без отсылок к внешним каталогам; их переносим в код и тесты.

### Секреты и конфиденциальные данные

| Данные | Где хранить | Запрещено |
|--------|-------------|-----------|
| `SECRET_KEY`, Stripe secret, DB password | только `.env` / секреты хостинга | код, Git, Docker image, логи |
| JWT refresh/access | access — memory SPA; refresh — `localStorage` + rotation | не логировать; не в URL |
| Пароли | хеш Django (`set_password`) | plain text, логи, API-ответы |
| Телефон | БД; в логах — маска `7***4567` | полный номер в error/log production |

**Перед каждым коммитом:** `git diff` — нет ключей `sk_`, `pk_live_`, паролей БД.
**Production:** `DEBUG=False`; при `DEBUG=True` и пустом `SECRET_KEY` — `ImproperlyConfigured`.

### SQL-инъекции и работа с БД

Django ORM **параметризует** запросы — основной защитный слой.

| Разрешено | Запрещено в production-коде |
|-----------|----------------------------|
| `Model.objects.filter(field=value)` | `RawSQL`, `.extra()`, `.raw()` с f-string |
| `Q()`, `F()`, `annotate`, `Exists` | конкатенация SQL: `f"SELECT ... {user_input}"` |
| `cursor.execute(sql, [params])` только если неизбежно | `cursor.execute(f"... {x}")` |
| миграции Django | произвольный SQL из request data |

**Правило code review:** любой `connection.cursor()` — отдельное обоснение в PR и тест.
Ввод пользователя (phone, title, body) — только через ORM, forms, serializers (валидация).

### XSS (SPA, admin и API)

- React: вывод user content через JSX (auto-escape); **запрещён** `dangerouslySetInnerHTML` для `Post.body`.
- Django admin templates: `{{ var }}` — auto-escape; `|safe` — **запрещён** для пользовательского контента.
- JSON API: `Content-Type: application/json`; клиент не интерпретирует как HTML.

### CSRF, CORS и сессии

- SPA: POST через JSON API с JWT — CSRF не требуется для `/api/*` (SessionAuthentication не default).
- Django admin и формы admin: CSRF стандартный.
- `@csrf_exempt` — **только в v2** (webhook Stripe + `Stripe-Signature`); в v1 не нужен.
- `CORS_ALLOWED_ORIGINS` из env: dev `http://localhost:5173`, prod — `https://<домен>` или HTTP IP ВМ.
- Production (`DEBUG=False`):
  - `CSRF_COOKIE_SECURE`, `SESSION_COOKIE_SECURE` — **только если** HTTPS (см. ниже);
  - `SESSION_COOKIE_HTTPONLY = True`, `CSRF_COOKIE_HTTPONLY = False` (стандарт Django);
  - `SECURE_SSL_REDIRECT = True` **только** за HTTPS/nginx с TLS; на ВМ с HTTP :80 — `False`,
    иначе redirect loop и 502 после deploy.

### Аутентификация и JWT

- Пароли: все validators из `AUTH_PASSWORD_VALIDATORS`; минимум 8 символов.
- JWT: короткий access (15 мин), refresh 1 день; `ROTATE_REFRESH_TOKENS = True` в production.
- Token endpoint: одинаковое сообщение при неверном phone/password (не раскрывать существование user).
- Brute-force: rate limit на `/api/token/` и register — **nginx** (итерация 1/7).

### IDOR и утечка paid-контента

- Чужой `Payment`, `Post` (edit/delete): **404**, не 403 — не подтверждать существование id.
- Paid `body`: только через `can_view_post_body()`; тесты list/retrieve API (guest, auth, subscriber).
- Serializers: явный `fields` / `read_only_fields`; не отдавать `stripe_*`, password hash.

### Ошибки и логи (без утечек)

- Production: кастомные `handler404/500` или стандарт Django без traceback клиенту.
- API: `502` для Stripe — общий `detail`, без текста SDK и stack trace.
- Логи: тип исключения + короткое сообщение; без request body с паролем, без Authorization header.

### Docker и PostgreSQL

- Образ: non-root user; `.env` через env Compose, не `COPY .env`.
- Postgres: отдельный user app с правами только на БД приложения (не superuser в prod).
- Порт 5432 наружу не публиковать; только internal network Compose.
- `CONN_MAX_AGE` + TLS к managed Postgres при деплое в облако.

### Контроль по итерациям (безопасность)

| Итерация | Обязательные меры |
|----------|-------------------|
| 1 | prod env; не expose DB port; nginx rate limit auth |
| 2 | hash паролей; normalize phone; CORS; AllowAny только register/token |
| 3 | paywall; queryset filter author; API без paid body |
| 4 | stripe secrets; idempotent `activate_subscription`; 404 payments |
| 5 | SPA не дублирует paywall; JWT не в URL; React escape |
| 6 | `check --deploy`; security tests; audit `git log -p` |
| 7 | secrets CI; SSH deploy; `.env` только на ВМ |

### Тесты безопасности (pytest)

- SQLi-smoke: злонамеренный ввод в title/phone (`' OR 1=1 --`) — 400/сохранение как строка, не ошибка
  SQL.
- IDOR: чужой post/payment → 404.
- Paid leak: list/detail API без body для guest и auth без подписки.
- Serializer: ответ register/token без поля password.
- (Итерация 6) при `DEBUG=False`: нет stack trace на `/api/health/` при forced 500 в тесте.

(Docker Hub + SSH + artifact SPA, по образцу **lms-backend**).

**Без** Redis/Celery в основном Compose — меньше сервисов, проще деплой и отладка.

### deploy-remote.sh

1. rsync (exclude `.git`, `.env`, `.venv`, `media`, `frontend/node_modules`, `frontend/dist`).
2. rsync `frontend/dist/` из CI artifact на сервер (stop nginx → clear dist → sync).
3. `docker login`; `compose pull web`; `up -d db web nginx`.
4. migrate в entrypoint; health check `/api/health/`.
5. Ошибка → trap восстановления stack; при нехватке disk — prune Docker.

### Prod settings (env)

- `DEBUG=False`; `SECRET_KEY` обязателен.
- `ALLOWED_HOSTS` — домен ВМ + `testserver` для CI.
- Secure cookies и `SECURE_PROXY_SSL_HEADER` за HTTPS/nginx.
- DB user без superuser; `CONN_MAX_AGE`.

- `README.md` → локально + ссылки на `wiki/ci-cd.md`, `wiki/frontend.md`.
- После деплоя: `curl http://<host>/api/health/`; логи `docker compose logs web nginx`.

## Стандарты кода (обязательно на всех итерациях)

Нормы ниже — **единственный источник** для docstring, комментариев и стиля в репозитории.
В коде и коммитах **не ссылаться** на внешние учебные каталоги; формулировки — самодостаточные.

**Принципы (PEP 20):** явность важнее неявности; ошибки не замалчиваются; читаемость
важнее краткости; простое решение предпочтительнее сложного.

### Соответствие PEP 8 и Zen of Python

**PEP 8 (код Python):** enforced через Ruff (`E`, `F`, `I`, `N`, `W`, `UP`), line-length **119**
(допустимо по PEP 8 как соглашение команды). Перед коммитом — `ruff check` + `ruff format`.
Код итерации 0 проходит проверки; каждая итерация — повторный прогон.

| Zen (PEP 20) | Как отражено в плане и будущем коде |
|--------------|-------------------------------------|
| Explicit is better than implicit | type hints, константы, `can_view_post_body()`, env для секретов |
| Simple is better than complex | ORM; один сервис stripe; sync activate в v1 |
| Complex is better than complicated | Stripe в сервисе, не в view; Celery — только v2 |
| Errors should never pass silently | logging + 502/404; без Celery retry в v1 |
| If the implementation is hard to explain… | матрица доступа; поток sync Stripe до кода |
| Practicality beats purity | sync success в v1; webhook — v2 при необходимости |
| There should be one obvious way | JWT; `activate_subscription`; `can_view_post_body` |
| Namespaces are one honking great idea | apps `users`, `posts`; `services/` |

**План (Markdown):** строки по возможности ≤ 119 символов (правило репозитория); при правках
длинные строки переносим. Таблицы допускают более широкие ячейки, если без разрыва смысла.

### PEP 8 и форматирование

- Длина строки: **119** символов (`pyproject.toml` → `[tool.ruff] line-length = 119`).
- Именование: функции/переменные `snake_case`, константы `UPPER_SNAKE_CASE`, классы `PascalCase`.
- Инструменты перед коммитом:
  ```bash
  poetry run ruff check .
  poetry run ruff format .
  poetry run mypy .
  poetry run pytest
  ```

### Структура Python-модуля (сервисы, validators, stripe, access)

Порядок элементов в файле:

1. Docstring модуля (назначение одним-двумя предложениями).
2. Импорты: stdlib → сторонние → локальные проекта.
3. Константы модуля (`UPPER_SNAKE_CASE`), без «магических» литералов в теле функций.
   Общие значения — в `config/constants.py` (см. ниже).
4. `_setup_logger()` → `logger = _setup_logger()` (модули с бизнес-логикой и интеграциями).
5. Публичные функции и классы.

### Константы, DRY и расширяемость

**Без магических чисел и строк:** любое повторяющееся или настраиваемое значение — именованная
константа в начале модуля или в `config/constants.py`.

| Где | Что хранить | Пример |
|-----|-------------|--------|
| `config/constants.py` | defaults JWT, Stripe, phone, pagination | `STRIPE_CURRENCY_MULTIPLIER = 100` |
| `config/settings.py` | чтение env поверх defaults из constants | `os.getenv("JWT_...", str(DEFAULT_...))` |
| модель | статусы, choices | `class PaymentStatus(TextChoices)` |
| сервис | HTTP-коды ответа API | константы модуля или `status.HTTP_*` |

**Запрещено в business-логике:** `* 100`, `== 11`, `"PENDING"`, `page_size=10` без имени константы.

**DRY — один источник правды (не дублировать):**

| Область | Одна реализация | Не дублировать |
|---------|-----------------|----------------|
| Доступ к paid | `users.services.access.user_has_active_subscription` | проверки в view и serializer |
| Тело поста | `posts.services.access.can_view_post_body` | отдельная логика в serializer и SPA |
| Bootstrap формы | `StyleFormMixin` | `form-control` в каждом `__init__` |
| Stripe | `users.services.stripe` | вызов SDK из view |
| Подписка | `users.services.subscription.activate_subscription` | логика activate в view/webhook |
| Телефон | `users.validators.normalize_phone` | regex в form и model |
| Entrypoint | `scripts/entrypoint.sh` | второй скрипт migrate+run |
| URL success/cancel | settings + `.env.example` | хардкод URL в view |

**Гибкость к изменениям:**

- Меняем сумму подписки → только `STRIPE_SUBSCRIPTION_AMOUNT` / env, не код view.
- Меняем TTL JWT → env + `DEFAULT_JWT_*` в constants.
- Новый статус Payment → добавить в `TextChoices`, миграция; сервис stripe без копипасты view.
- Новое правило доступа → расширить `can_view_post_body`, тесты матрицы; views не трогать.

**Перед добавлением функции:** искать существующую в `services/`, `validators/`, mixins.
Если нужно в двух apps — вынос в `users` или `posts.services`, не копировать.

**Django-исключения:** `models.py`, `admin.py`, тонкие `views.py` — docstring модуля и типизация
методов обязательны; полный `_setup_logger` — в сервисах, validators, management commands.

### Docstring (Google style, русский язык)

Обязательны для **всех публичных** функций, классов, методов сериализаторов и сервисов:

```python
def normalize_phone(value: str) -> str:
    """Приводит номер телефона к единому формату для хранения и сравнения.

    Args:
        value: Введённый номер (может содержать +7, 8, пробелы, скобки).

    Returns:

    Raises:

    Example:

        '79001234567'
    """
```

- Описывать **поведение**, не «см. документацию Stripe» без контекста.

### Итерация 4: Stripe и подписка (риск: очень высокий)

**Неявные факторы:** async оплата; двойной Checkout; success URL до confirm в Stripe.

#### Поток оплаты v1 (sync):

```
POST /api/payments/create/ → Payment(PENDING) + payment_url
→ Stripe Checkout → STRIPE_SUCCESS_URL?session_id=...
→ GET success: sync status в Stripe API → activate_subscription(payment_id)
→ Payment PAID, Subscription.is_active=True
```

#### Шаги:
1. `Payment`, `Subscription` OneToOne user.
2. `users/services/stripe.py`: multiplier из constants; `StripeServiceError`.
3. `users/services/subscription.py`: **`activate_subscription(payment_id)`** — единственная точка
   активации (atomic, idempotent, `select_for_update`).
4. create: idempotency — повторный POST → тот же PENDING url.
5. Success API/view: проверка session_id → Stripe API → `activate_subscription`.
6. чужой payment → **404**; Stripe error → **502**.
7. `STRIPE_SUCCESS_URL` — страница SPA или `templates/payments/success.html` → redirect в SPA.
8. `user_has_active_subscription` читает `Subscription.is_active`.

#### Типичные баги и профилактика:
| Баг | Профилактика |
|-----|--------------|
| 990 ₽ → 99000 коп | `unit_amount = amount * STRIPE_CURRENCY_MULTIPLIER` |
| два PENDING / двойная оплата | idempotency в create view |
| success до paid в Stripe | sync через Stripe API перед activate |
| повторный success | idempotent `activate_subscription` |
| утечка stripe ids в JSON | serializer: только url и status |

#### Тесты итерации:
- mock stripe: create, idempotency, success activate, 502, 404 чужого payment.

#### Качество:
- `users/services/stripe.py` — структура модуля с `_setup_logger`; docstring у публичных функций.

#### Безопасность:
- `STRIPE_SECRET_KEY` только settings/env; 502 без текста Stripe; PaymentSerializer без
